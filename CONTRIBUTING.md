# Contributing to atlas-richie-ai

**Languages:** [English](CONTRIBUTING.md) | [中文](CONTRIBUTING.zh.md)

Thank you for your interest in contributing to `atlas-richie-ai`.

## Principles

- Contributions should align with project goals and respect module boundaries.
- Ensure the code compiles, tests pass, and documentation is updated before submitting.
- All contributions are licensed under the repository root [LICENSE](./LICENSE) (Apache License 2.0).

## Contribution Workflow

1. Fork the repository and create a feature branch (e.g. `feature/<name>` or `fix/<name>`).
2. Develop and self-test locally; avoid introducing build failures.
3. Open a Pull Request describing:
   - Motivation
   - Main changes
   - How you verified the change
   - Compatibility impact (if any)
4. Iterate based on review feedback until merged.

## Commit Guidelines

- Use clear, imperative commit messages; explain **why** before **what**.
- Update README or module docs when public APIs, configuration, or behavior changes.
- New configuration options should have sensible defaults and examples to avoid breaking existing users.

## Code Style

- All public classes, fields, and methods carry **Chinese Javadoc** (`@param` / `@return` / `@throws`).
- Follow the existing module structure — each Spring AI adapter ships as a 4-module set:
  - `*-store` (the `VectorStore` implementation)
  - `*-autoconfigure-*` (Spring Boot auto-configuration)
  - `*-starter` (BOM-style convenience starter)
  - `*-bom` (optional, only when multiple adapters live in the parent)
- One VectorStore per top-level package; no cross-store dependencies.

## Code of Conduct & Security

- Be professional, respectful, and constructive. See [CODE_OF_CONDUCT.md](./CODE_OF_CONDUCT.md) / [CODE_OF_CONDUCT.zh.md](./CODE_OF_CONDUCT.zh.md).
- Do **not** disclose security issues publicly. Follow [SECURITY.md](./SECURITY.md) / [SECURITY.zh.md](./SECURITY.zh.md).

## Local Build

This project requires **Maven 3.9+ or Maven 4.0+** (uses `<modelVersion>4.0.0` + hardcoded `<version>1.0.0-SNAPSHOT</version>`).  Recommend **Maven 3.9.x** for deploys to CNB — Maven 4.0.0-RC5's JdkTransporter has an auth-flow issue with CNB's 401 responses (no `WWW-Authenticate` header).

```bash
# Unit tests for a single module
mvn -pl vector-stores/atlas-richie-ai-vikingdb-store test

# Full reactor build + test
mvn clean verify
```

## Publishing (maintainers only)

Use the bundled scripts in `scripts/` instead of running `mvn deploy` directly. They encode all
the required flags and pre-flight checks.

```bash
# SNAPSHOT → CNB private server (integration testing)
./scripts/release.sh snapshot

# release → Maven Central via Sonatype Central Portal
./scripts/release.sh release

# Validate without deploying (CI演练 / PR check)
./scripts/release.sh dry-run
```

Windows / IDEA users: `scripts\release.bat <mode>` — works identically.

### One-time setup (release machine)

Before the first release, generate a GPG key on the machine that will sign:

```bash
./scripts/setup-gpg.sh
# 1. install gpg if missing
# 2. generate a new key (interactive)
# 3. upload public key to keys.openpgp.org
# 4. prints the <profile> snippet to add to ~/.m2/settings.xml
```

Server credentials (`~/.m2/settings.xml`) live in three `<server>` entries:

| `<server><id>` | Used for |
|---|---|
| `richie696-repo-richie-snapshot` | CNB SNAPSHOT repo |
| `richie696-repo-richie-release` | CNB release repo |
| `central` | Sonatype Central Portal |

Plus the `gpg` profile (`<gpg.keyname>` + `<gpg.passphrase>`) generated by `setup-gpg.sh`.

### Why a script, not raw `mvn deploy`?

IDEA's built-in packager cannot pass Maven flags (`-Dgpg.skip=true`, `-Dmaven.deploy.skip=true`).
The script wraps them so they cannot be forgotten. The `release.sh` script:

- pre-flights `mvn` and `gpg` are on `PATH`
- uses the right flag combination per mode
- prints a clear banner so the operator knows what is about to happen
